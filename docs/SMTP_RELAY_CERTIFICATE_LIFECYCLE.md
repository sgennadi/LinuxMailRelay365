# SMTP Relay certificate lifecycle

Separate SMTP client TLS certificates from Entra OAuth signing certificates.
Linux hostname and selected Exchange Accepted Domain are independent.
Support existing PEM, imported PFX and ACME providers only after verifying client TLS suitability. Do not assume Let's Encrypt is eligible.

The read-only checker validates expiration, local CA chain, DNS name, key match and OpenSSL sslclient purpose. It deliberately does not authorize deployment or prove Exchange acceptance.

The Windows import action ships its own checker, stager and receiver through an isolated Python launcher. On a connected Postfix host with Python 3, OpenSSL and root or passwordless sudo, no previous LinuxMailRelay365 helper installation is required. Only public helper code and the DNS name travel in command arguments; the certificate package travels through SSH stdin. The temporary helper directory under `/run` is private and removed after normal completion or handled failure. Validated certificates are staged under `/etc/postfix/lmr365-smtp-tls`, without modifying active Postfix settings or Exchange connectors. Password-based sudo, production SELinux acceptance, ACME issuance and renewal, and end-to-end Exchange delivery still require separate work.

Renewal design: Linux-native scheduler, restricted DNS credentials, staged certificate and key, validate chain/name/purpose/key, atomic activation, Postfix reload, delivery verification and rollback. Manual DNS challenges must not be labeled automatic renewal. Preserve local delivery and existing listeners. Never modify inbound TLS when configuring outbound TLS.

## ACME DNS-01 readiness (read-only)

The Windows SMTP certificate wizard opens a separate DNS-01 plan for the manually selected Exchange domain and independent certificate DNS name. The connected Linux host uses its configured resolver through `dig`, if available, to inspect TXT, CNAME, direct CAA and selected-domain NS answers. Only answer states are returned; TXT contents are not exported. Missing tools, NXDOMAIN, resolver errors and empty answers remain distinct. Certbot executable detection is not a plugin or credentials check. The plan SHA covers inputs only, not DNS observations. Effective CAA (including inheritance and aliases), public DNS propagation, domain ownership, Exchange acceptance and certificate client TLS eligibility remain unverified. No Certbot invocation, issuance, credential collection, DNS update, renewal or Postfix activation is performed.

## Renewal inventory (read-only)

The SMTP TLS wizard inspects standard Certbot and isolated LinuxMailRelay365 renewal configurations, the presence of a protected (not validated) renewal profile, and five systemd timer/service states. Configuration and hook contents, DNS credentials and private keys are not exported. Unsafe paths, missing configurations, ambiguous settings and systemd failures remain distinct. An active timer does not prove successful renewal. The existing managed service may activate renewed material; the inventory does not invoke or enable that service, run Certbot, execute hooks or reload Postfix. Dry-run, credential verification and actual activation remain separate actions.

## Reviewed staging renewal test

The renewal inventory now offers a separate Review and test renewal action for an existing isolated managed profile. It ships the read-only review and dry-run helper plus its dependencies, requires a single matching certificate DNS SAN, private root-owned configuration and credential files, supported DNS authenticator, known Let's Encrypt directory and no configured hooks, custom global configuration or unsupported options. A fresh plan SHA is checked again under the managed renewal lock after explicit approval. The test uses the staging CA and `--dry-run` only; temporary DNS TXT updates and local Certbot state/logs are possible. It never invokes live renewal, forced renewal, activation or Postfix reload. Failed/uncertain tests must be investigated before retry. Custom CA and unsupported configuration remain manual. Staging acceptance is not evidence of production CA, client TLS or Exchange delivery acceptance.

## Exchange certificate binding review

The SMTP TLS wizard can perform a fresh local managed certificate review, inspect the exact Exchange Online tenant and accepted domains, then repeat the local SHA review. The certificate identity is independent of the sender domain, and this conservative workflow requires the exact DNS SAN and an exact accepted domain for both identities. Wildcard, CN-only, foreign certificate syntax and ambiguous existing connectors require manual review. The existing connector creation screen takes an explicit certificate DNS identity rather than substituting the sender domain; certificate creation checks exact accepted domain and overlap, sets RequireTls, and verifies the resulting identity. The new binding action is read-only and does not set route approval or create/change a Connector. Neither configuration observation nor local certificate validation proves Exchange acceptance or mail delivery. See Microsoft Learn: https://learn.microsoft.com/exchange/mail-flow-best-practices/how-to-set-up-a-multifunction-device-or-application-to-send-email-using-microsoft-365-or-office-365 .

## Primary Postfix delivery probe

The Connector wizard now offers a separate two-message acceptance probe through the installed primary Postfix sendmail submission interface. Preview requires a single primary instance, the selected Microsoft 365 MX on port 25, mandatory outbound TLS and no unsupported dynamic route or rewrite settings. Each explicitly approved run ID is reserved in a private persistent ledger before any submission; an attempted or uncertain run cannot be resubmitted with that ID. Trace can be repeated without sending mail and matches the unique Message-ID, queue ID, exact recipient, DSN and observed MX from bounded recent journal records and the Postfix JSON queue. Local acceptance, deferred, bounced, observed Exchange relay acceptance and unknown correlation are distinct. Domain comparison does not prove tenant recipient membership, and local root submission does not test application SMTP AUTH. No configuration, queue maintenance or retry command is invoked; ordinary Postfix delivery retries still apply. Journal-only correlation can be unavailable (including rotated logs or alternate syslog configurations); queue absence is not delivery proof. No TLS handshake or inbox receipt claim is made. The supported probe is intentionally limited to simple direct primary connector routes; isolated instances, policy maps, alternate transports and custom mail log backends need separate support.

## Exchange Online Message Trace V2

The primary Postfix delivery dialog can query the intended Exchange tenant for a recorded run. A fresh local ledger check supplies the start time and attempted roles. The exact local request SHA-256 is verified in the GUI before the cloud query. The operator must select the exact tenant and sender accepted domain. The read-only PowerShell 7 helper uses Get-MessageTraceV2, exact sender, recipient and Message-ID filters, a seven-day local run limit and bounded results; it verifies tenant before and after each query. It returns role/status/count and run identity. Ambiguous or absent records remain distinct. Request/result files are restricted to the current Windows account and cleaned after the process exits; interrupted application processes may require manual cleanup. ExchangeOnlineManagement, trace permissions and accepted-domain read permissions must already exist. No Graph permission is provisioned, no tenant changes or automatic resend are performed. Service-reported Delivered does not prove inbox visibility, TLS handshake or exact connector identity. Trace indexing can lag. See https://learn.microsoft.com/powershell/module/exchange/get-messagetracev2 .

## STARTTLS connectivity diagnosis

The primary Postfix delivery dialog offers a no-mail STARTTLS test from the connected Linux host using the selected Microsoft 365 MX on TCP 25. It resolves public addresses, pins a sampled IPv4 and IPv6 address (one per available family), performs EHLO and STARTTLS with TLS 1.2+ and system trust/hostname verification, and reports numeric SMTP codes, negotiated protocol/cipher, public peer certificate SHA-256, issuer, validity and DNS SANs. It distinguishes DNS, connection, SMTP and TLS errors without exporting raw SMTP responses. No client certificate, AUTH or SMTP envelope is supplied and no settings or queue contents are changed. This test does not run Postfix's SMTP process, check every DNS answer, prove certificate presentation, verify the tenant connector or prove delivery. The standard Microsoft 365 public MX suffix is the only supported target in this screen.

## Managed client certificate STARTTLS diagnosis

The optional second STARTTLS mode uses the active protected managed Postfix generation after explicit approval. It verifies the selected MX against the configured relayhost, rejects custom routing/TLS policy maps, validates managed generation integrity and terminal journals, and checks configuration snapshots before/after loading and probing. The SSL context loads the original root-only chain and private key on Linux, never exports or copies the key, and refuses encrypted-key prompts. Server trust and hostname verification are mandatory. A loaded client certificate means it is available for the TLS handshake if requested; actual presentation, remote acceptance, Postfix process behavior, connector recognition and delivery are not verified. This mode requires root or the existing sudo path, and only the managed primary Postfix route is supported. No mail is submitted or configuration changed.

## Inactive staged certificate STARTTLS (Linux helper)

The managed STARTTLS helper also accepts an explicit `TEST_STAGED_CLIENT_CERTIFICATE` request with the selected Microsoft 365 public MX, candidate ID and certificate DNS identity. It holds the managed deployment lock, rejects the active generation, revalidates the private candidate's integrity and strict local TLS eligibility, and uses the root-only files to establish the same verified STARTTLS connection without AUTH or an SMTP envelope. The active pointer and candidate integrity are checked before and after the network probe. The lock file and temporary public certificate validation files may be created. The TLS peer may request the client certificate; private keys never leave Linux. The test does not modify Postfix, activate a candidate, verify actual client certificate presentation or prove connector recognition/delivery. The reviewed deployment dialog offers Test staged certificate STARTTLS with an explicitly entered tenant MX and separate confirmation. It invalidates any prior activation approval, reports each sampled address, and requires a fresh deployment review before activation.

## Public MX discovery in the staged deployment dialog

The reviewed TLS deployment window inherits the selected accepted domain and saved route MX, and automatically observes MX records from the connected Linux host via public resolver 1.1.1.1 (`dig` is required, no root required). Discover MX repeats the bounded lookup. The unique lowest-preference record is proposed only when every observed MX has the Microsoft 365 public suffix and the preferred target is unambiguous; a configured or manually entered address is never overwritten. A gateway, mixed targets, tied preferred records, null MX, aliases, DNS errors or unavailable dig require manual tenant MX review. The DNS name is sent to the public resolver, and DNS evidence is not proof of tenant ownership or connector acceptance. No route, Exchange, Postfix configuration or mail queue changes. The existing explicit STARTTLS confirmation and fresh deployment review remain required.

## Guided SMTP connector setup

The certificate setup window now uses Back/Next contextual pages instead of displaying every action together. Public IP mode skips certificate-specific pages; certificate mode presents identity/source, certificate preparation, staged MX/STARTTLS and deployment, active Exchange binding, delivery and maintenance. All original operations retain their existing reviewed dialogs, explicit confirmations, and runtime safety gates. Navigation is not approval or evidence of success. The MX and certificate identity selected in the deployment dialog are carried within this wizard session; they do not overwrite the saved route. The delivery probe uses the session MX and still reviews the actual primary Postfix configuration. Active binding requires a deployed managed certificate, and tenant connector creation remains a separate existing workflow. Existing-certificate validation alone does not stage material. No automatic activation, connector creation, message send or renewal is triggered by Next.

## Staged certificate connector identity preflight

The root-only candidate-binding-preview operation validates a selected staged generation, exact DNS SAN, chain, private key and existing strict sslclient purpose. It binds the candidate, certificate evidence, CA bundle and observed active pointer into a local review SHA under the deployment lock. No Postfix installation status, active TLS configuration, DNS operation or cloud mutation is required. It does not prove Microsoft 365 acceptance; the exact tenant/domain and connector must be reviewed separately.

The deployment dialog now exposes Review Exchange Connector and Preview / create NEW Connector against the selected staged certificate. It validates the local staged identity before and after the read-only cloud inspection or creation preview; creation additionally requires the main accepted-domain approval, exact tenant and typed confirmation, then another local review and the existing SHA-checked cloud Apply. Existing connectors are not edited by this action. No automatic Postfix activation or mail sending, and activation requires a fresh deployment review. The exact certificate DNS name must itself be an accepted domain, as in the existing conservative cloud workflow. Cloud creation and local activation are separate transactions; failure or interruption requires tenant reinspection before retry.

The setup wizard also opens a focused Exchange Connector inventory (no selected OAuth app or Graph sign-in required). It lists the existing inspector's matching connector candidates and reuses the tenant-marker, exact-object, reviewed-SHA and typed-confirmation management path for Enable, Disable, Rename and Delete. Unverified ownership is read-only; rename/delete require a disabled connector. A successful or uncertain mutation requires a new inventory before another operation. Local route approval is invalidated conservatively; the actual Linux configuration is not modified. Existing general cloud inventory and management entry points remain available.

## Reviewed connector settings edit (backend)

The existing object manager supports `EditSettings` only for a disabled, tenant-stamped OnPremises Connector. Exact accepted sender domains and either exact public IPv4 addresses or an exact certificate accepted domain can be replaced; authentication mode and existing security switches are preserved. Wildcards, CIDR ranges other than individual /32 addresses, ambiguous identities, hybrid/internal-trust connectors, overlap with other connectors and unknown certificate syntax require manual review. Review binds all connector state and proposed values into the SHA. Apply repeats live checks and requires a precreated empty Windows file with a private current-account ACL; it writes and flushes a JSON backup of the previous settings and reviewed proposal before calling Set-InboundConnector. Postcheck validates disabled state, selected values, unchanged security fields and other connector inventory. Backup is configuration evidence, not an automatic restore package. Live tenant validation remains required. Cmdlet reference: https://learn.microsoft.com/powershell/module/exchangepowershell/set-inboundconnector .

The focused Connector inventory now offers EditSettings for disabled tenant-owned objects with one authentication mode. A separate form shows editable sender domains and the existing identity type. Live Review and Apply reject stale inventory values; the confirmation displays old and proposed settings, exact tenant, object, SHA and backup path. The app creates the private empty backup only after typed consent and retains written backups even on uncertain outcomes. No automatic re-enable or restore is performed. Public IP creation and restore from backup remain separate follow-up work.

## Reviewed settings restore

Select a disabled managed Connector and RestoreSettings in its focused inventory. Choose an earlier JSON settings backup. The app validates the exact tenant, object name and identity, schema, bounds, authentication mode and old/proposed settings. Current inventory must match the saved proposal, so an unrelated later edit is not silently overwritten. Live Review and Apply additionally require the five saved security flags to match the current Connector. The old values go through the same accepted-domain, conflict, fresh SHA and backup-before-Set checks as EditSettings, with separate RESTORE M365 CONNECTOR typed approval. A second private backup preserves the pre-restore settings. The original snapshot is unsigned and is not proof of a successful earlier Apply; review the displayed values. This restores supported settings only, not deleted objects, renamed objects, security policy, enabled state or unrelated Connector properties. No automatic re-enable, Postfix or DNS change occurs.

## Public IPv4 connector preflight (backend)

The unprivileged Linux STARTTLS helper supports an explicit observe_public_ipv4 request. It performs direct IPv4 HTTPS GET requests to api.ipify.org and checkip.amazonaws.com with bounded curl timeouts, no user curl config, no proxy, no redirect or disabled TLS verification. Both providers see the Linux host's HTTPS egress address. A suggestion is returned only if both valid public addresses agree. Failure or disagreement never guesses an IP. HTTPS observations cannot establish static/exclusive ownership, SMTP NAT or the source used by Postfix. Existing Microsoft 365 MX STARTTLS remains a separate no-mail check. The cloud Connector manager supports read-only Inspect for an exact public IPv4, reporting matching, incompatible or ambiguous identities; unknown address/range syntax is conservatively refused in creation. These are configuration observations, not proof of delivery. No service installation or change to local mail configuration is performed.
