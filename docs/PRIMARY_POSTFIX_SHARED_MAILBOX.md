# Primary Postfix: shared mailbox migration candidate

This is a read-only, exact-byte candidate for the primary Postfix only. The
existing GUI Preview now returns the original config SHA-256, candidate
SHA-256, a mailbox-bound plan SHA-256, and a fixed allowlist of changed entries.
It does not save the candidate, install packages, provision identities, contact
Microsoft, send mail, or start/stop/reload services.

The planned changes are default_transport, relay_transport, clearing a former
relayhost, the dedicated pipe's recipient/concurrency limits, and adding the
pipe if absent. Unrelated lines and continuations are preserved byte for byte.
Local/virtual delivery and SMTP listener settings are not intentionally changed.
Ambiguous syntax, duplicate/continued target definitions, dependent macros,
conflicting routing, or unexpected pipe definitions block the candidate.

The candidate is not proof of effective Postfix configuration, certificate
signing, SMTP AUTH, sender authorization, or successful mail delivery. Its
plan SHA is not an Apply authorization and the identity field records only
the observed mailbox-match state. Before enabling Apply, require native
candidate validation, identity fingerprint binding, verified backup, a
maintenance-window/queue guard, rollback, and real distro coverage.
Do not use the destructive Force Replace path as a substitute.

## Native alternate-configuration comparison

Preview v3 adds a root-only, short-lived `/run/lmr365-primary-native-*` scratch directory. It copies the original and proposed exact bytes sequentially to the same alternate config root and uses only native `postconf -c` reads: explicit parameters, selected expanded address-class/listener/policy settings, master services and service overrides. It first requires a normalized baseline equal to the live native snapshot, then allows only the reviewed transport parameters and exact dedicated pipe to differ. The live configuration and native snapshot are checked again, and scratch copies are removed. The report contains only status and SHA-256, not native output or configuration values. A verified native digest is bound to the plan; native mismatch, unsupported syntax, diagnostics, or drift require review and cannot authorize Apply. This is parser evidence, not a live daemon, map evaluation, address-resolution, identity, SMTP AUTH or mail-delivery proof. No service control, live file write, package installation, `postfix check`, or queue operation is introduced. The proposed route is still single-mailbox only; multi-mailbox primary routing, backup/restore, SELinux writes and native distro acceptance remain separate gates.

## Exact two-file offline transaction core (experimental)

The new `linux/primary-mailbox-transaction.py` is a library, not an operational CLI. It binds the original/proposed exact files, ownership/mode, directory identity, native before/after fingerprints, selected mailbox identity/certificate and caller-supplied installed-runtime evidence. Only simple non-OAuth routes without an existing dedicated OAuth pipe qualify. Both before/after files are durably backed up in a private SHA-bound directory before mutation. Apply adds master.cf's pipe before changing main.cf; Restore reverses the order. The intermediate old-main/new-master pair is recognized after interruption; foreign or impossible mixed states refuse Restore. No service, queue, credential or tenant action is performed by the library. Mandatory stopped-instance, empty-queue, exclusive maintenance, installed-runtime and fresh no-mail SMTP AUTH callbacks must still be integrated and tested on a real host. Unit tests exercise actual file changes in temporary directories, with synthetic runtime/native evidence. SELinux labels and ACLs are not supported by this initial core. GUI Apply remains disabled.

## Installed runtime and real no-mail SMTP AUTH review

The experimental `manage-primary-mailbox-offline.py --review` entry point supplies the transaction core with actual stopped-instance/empty-queue/exclusive-maintenance guards and a primary software-PEM runtime guard. Run only from a trusted root-owned bundle containing the matching project Linux helpers. Supply `--mailbox`, `--tenant-id`, `--client-id`, `--confirm VERIFY_PRIMARY_MAILBOX_SMTP_AUTH` and `--maintenance-confirmation I_HAVE_PREVENTED_CONCURRENT_MAIL_AND_CONFIG_CHANGES`. It obtains the existing route and OAuth rotation locks, checks the exact active identity, certificate/key pair, local dedicated service UID/GID, installed transport and signer bytes against the bundled copies, and invokes only the fixed `--smtp-auth-check --config /etc/postfix/m365-oauth/app.json` diagnostic as that account, with a sanitized environment. The subprocess must return exactly the known success line and no stderr. No token, private key, identity contents or raw SMTP transcript are returned. A stable runtime SHA binds the selected identity, code, key/cert digests and account/system-executable evidence. A short in-process 90-second authentication observation is reused only while the full snapshot remains identical; it is never persisted or reused across CLI processes. The review validates the native before/after candidate and returns only the plan SHA and runtime SHA. Unknown runtime versions, hardware identities, ambiguous import artifacts, extra service groups, drift, AUTH failure, missing permissions, SELinux and nonempty queues cause refusal. No production Apply/Restore command, installation, service start or message submission is enabled by this change. The service-account test is not proof of a running Postfix pipe's SELinux domain or delivery. Native stopped-host and real-tenant acceptance are still required.

## Experimental operational offline Apply and Restore

The primary single-mailbox manager now accepts four mutually exclusive operations. All require root and `--maintenance-confirmation I_HAVE_PREVENTED_CONCURRENT_MAIL_AND_CONFIG_CHANGES`, stopped Postfix, the exact default `/etc/postfix` / `/var/spool/postfix` single instance and `mail_owner=postfix`, and verified empty queues. Both route and OAuth rotation locks are held. The expanded native scope is checked again during every maintenance guard; checking an unrelated spool is not sufficient. Retain the Review SHA before applying.

- `--review --mailbox MAIL --tenant-id TENANT --client-id CLIENT --confirm VERIFY_PRIMARY_MAILBOX_SMTP_AUTH` produces a SHA-bound plan with fresh no-mail authentication.
- `--apply --mailbox MAIL --tenant-id TENANT --client-id CLIENT --expected-sha256 SHA --confirm APPLY_STOPPED_PRIMARY_MAILBOX_ROUTE --auth-confirmation VERIFY_PRIMARY_MAILBOX_SMTP_AUTH` repeats the full review with new in-process AUTH evidence; backs up both configurations under `/var/lib/linuxmailrelay365-primary-mailbox-recovery/SHA`; applies the exact two-file transition and checks the native readback. Failure may trigger guarded rollback. Any failed or interrupted write operation is treated as uncertain until the recovery record is inspected.
- `--inspect-backup SHA` reads the protected recovery pair. `before` and `after` additionally require matching native snapshots; `pipe_only` means the exact intermediate pair is observed, not ready to start. Missing, tampered or foreign state is refused.
- `--restore SHA --confirm RESTORE_STOPPED_PRIMARY_MAILBOX_ROUTE` restores the exact original pair, including a recognized intermediate pair. It intentionally does not authenticate to Entra or SMTP, so OAuth/network failure does not prevent recovery. No foreign edit is overwritten.

The manager never stops, starts, reloads, submits mail or changes queues. It emits only fixed statuses and SHA identifiers, not configuration bytes or exceptions. A recovery identifier on a failed operation does not establish that a complete backup exists. Retain the SHA and inspect before retrying. The operator must keep submissions, service starts and external edits blocked. PEM identity only; no SELinux/ACL file support, GUI Apply, actual Postfix pipe delivery or live tenant acceptance is claimed. Do not deploy to a production host on the basis of mock-based CI alone.
