# Staged ACME renewal

The supplied systemd units renew isolated Certbot lineages twice daily.
Install only after reviewing the root-owned renewal configuration and all
configured hooks. --no-directory-hooks does not disable per-lineage hooks.
ProtectSystem restricts filesystem writes but is not a complete hook sandbox.
Do not point Postfix at the ACME live symlinks: renewal is staging only.
A separate validated deployment transaction is required. The timer does not
prove CA compatibility or successful delivery. Inspect the service exit
status and private Certbot logs. Units are not enabled automatically.

After review, install the two units in /etc/systemd/system, run
systemctl daemon-reload and enable --now linuxmailrelay365-smtp-acme-renew.timer.
No existing Certbot timers need to be disabled.

## Reviewed GUI systemd management

The SMTP certificate wizard ships the seven managed systemd units and their runtime dependencies. The new screen checks installed file hashes and effective unit paths, rejects conflicts/overrides, and installs missing files without overwriting existing ones or starting the timer. A partial installation may leave newly created runtime files for a reviewed retry. Enabling boot recovery, enabling/starting/stopping/disabling the timer and requesting live renewal are separate reviewed and confirmed actions. Live operations require the production Let's Encrypt renewal profile, local TLS preflight and enabled recovery units. They use the existing service, which can activate renewed material in Postfix. A persistent timer may trigger immediately. Stopping the timer does not cancel an in-progress service. Next/last trigger and service result are observed, not a proof of successful renewal or delivery. The schedule is the packaged twice-daily schedule; editing the schedule, updating conflicting units and uninstalling remain separate work. SELinux-active hosts are blocked for live operations in this screen. Existing ordinary Certbot timers are not changed. External administrators must not edit the units or configuration concurrently. Real systemd, CA and mail delivery tests remain required.

## GUI public DNS provider discovery

The ACME plan dialog now exposes provider discovery separately from local resolver readiness. The connected Linux host queries one explicitly identified public resolver (1.1.1.1) for the public DNS zone and challenge CNAME/NS evidence, with a bounded query count, per-query timeout and total DNS budget. It checks installed Certbot authenticator registration, not credentials, and offers a candidate only when exactly one registered provider matches a non-delegated DNS hint. The administrator explicitly selects the suggestion. CNAME or directly observed challenge NS delegation requires manual review; absence of a direct record is not proof that every possible delegation is absent. DNS/provider failures do not authorize issuance; the existing manual/readiness plan remains available. Public DNS names are sent to the resolver, and Certbot plugin inventory may use its ordinary local logs. No DNS write, certificate issuance, Postfix change or Microsoft 365 authorization is performed. Root or the existing sudo path is required to inspect Certbot plugins; missing dig or failed public DNS access is reported as unavailable.

## Local issuance readiness review

The ACME dialog now opens a separate read-only issuance review for a selected automatic DNS provider. It offers the explicit Let's Encrypt staging or production endpoint (staging is the default), account contact and an existing absolute ASCII credential-file path on Linux. The credential contents remain on the server; only structural status and registered Certbot authenticator status are returned. Credential files must be regular, root-owned, private, single-link files; parent directories must not be writable by non-root. Parser failures are deliberately sanitized. The review identifier binds normalized request fields and public report status, not credential contents, and is not an execution authorization. No DNS API credentials are tested remotely, no certificate is issued and no DNS, Postfix or Microsoft 365 configuration changes are requested. A later, explicitly approved staging challenge and issuance workflow is required. Existing manual planning and renewal remain available.

## Reviewed staging DNS-01 challenge

The local issuance review now offers an explicit staging-only DNS-01 test after a successful fresh local review. It binds the exact request to the review identifier, repeats structural/plugin checks, checks credential file identity and uses a root-private nonblocking lock to exclude concurrent invocations of this new helper on the same Linux host. A separate confirmation names the public TXT owner and provider, warns that the plugin creates/removes records and requires the administrator to exclude other renewal/challenge activity. The test refuses an unavailable baseline, observed CNAME/NS delegation or any existing TXT answer. It invokes Certbot only against the Let's Encrypt staging CA using --dry-run, isolated temporary config/work/log/home directories, --config /dev/null and --no-directory-hooks. After an attempted run it compares the public TXT snapshot via 1.1.1.1, exposing counts/status only, never TXT values or credential contents. A matching cached snapshot is not authoritative cleanup proof; interrupted connections and timeouts can leave records, which must be reviewed manually. No manual deletion, production issuance, Postfix configuration change or Exchange activation. The lock does not coordinate other Certbot clients or hosts. Production evaluation is a separate, explicitly approved operation as described below.

## Production certificate evaluation (no Postfix activation)

After a staging DNS-01 success and unchanged observed TXT snapshot, the Linux helper may create a single-use root-private receipt in /run. It is bound to the normalized production request and credential file identity, expires after 15 minutes, is replaced/invalidated by another staging test on that host and is consumed under the same nonblocking lock before production. The GUI permits a production review for 14 minutes after receiving the receipt and invalidates it when contact or credential path changes. The server independently checks expiry, request and credential identity. This is staging evidence, not proof of authoritative DNS cleanup or Microsoft 365 acceptance. The operator explicitly authorizes CA terms, DNS changes and production issuance. The new lineage is reserved under /var/lib/linuxmailrelay365/smtp-acme-evaluation/<certificate-name>, with private isolated config/work/log/home state; existing directories are refused, including failed or uncertain attempts. No automatic deletion, retry, production renewal profile, staging into Postfix or activation. Certbot uses the fixed Let's Encrypt production directory, no global cli.ini or directory hooks. The helper independently checks trusted chain, hostname, lifetime and key match, reports certificate fingerprint and explicit client-auth EKU, and separately checks OpenSSL sslclient purpose. Let's Encrypt has removed client authentication EKU from new certificates; Microsoft SMTP relay requirements do not mandate it. Local sslclient refusal is not proof of Exchange rejection, and the existing activation gate remains unchanged. A successful local evaluation does not establish real Postfix handshake or connector acceptance. Receipt and evaluation features require root or existing sudo access. Real CA and provider tests remain outstanding.

## Reinspect retained evaluation

The issuance review now includes **Inspect existing evaluation**, independently of staging evidence, contact email and credential-file inputs. The Linux helper takes only the selected accepted domain and certificate name, resolves the fixed evaluation path, and uses the same nonblocking ACME lock as staging and production (the lock file and temporary helper workspace may be created). It reports `not_found`, `unverified` or `material_verified` after checking the retained directory and, if possible, the certificate chain, hostname, validity, key match, SHA-256 fingerprint and local client-auth purpose. A missing or invalid certificate inside an existing directory is `unverified`, not permission to reissue. No DNS query, Certbot invocation, receipt consumption, lineage creation/deletion, Postfix activation or Exchange action is requested. Inspection is not proof of the original CA outcome or DNS cleanup. Preserve incomplete or uncertain state for administrator review.

## Reviewed staging of retained material (Linux helper)

`reviewed-smtp-acme-production.py --stage` accepts a JSON envelope containing `request` (the same two domain/name fields as inspection), `confirm` (`STAGE_REVIEWED_EVALUATION`) and the reviewed lowercase SHA-256 certificate fingerprint (`certificate_sha256`). Under the shared ACME lock, it repeats the local inspection and refuses unless the chain/name/key and existing strict sslclient gate pass and the fingerprint matches. The existing protected stager verifies the copied files and checks their DER certificate fingerprint before publishing a candidate. The candidate is separate from active Postfix configuration; no activation, reload, DNS change, reissuance, renewal profile or Exchange change occurs. The helper does not claim Exchange acceptance. An uncertain staging result requires candidate inventory review. The GUI offers Stage reviewed certificate only after a successful retained-material inspection with sslclient passed, requires a separate confirmation of the fingerprint, and directs the operator to the existing deployment review. Server-only certificates failing the local purpose check remain evaluation-only.
