# SMTP TLS activation primitive

The generation pointer helper is internal only. It must not be invoked by a GUI
or timer until a deployment transaction supplies an exclusive lock, certificate
revalidation, a durable recovery journal, Postfix configuration verification,
reload and delivery checks. A pointer swap alone does not guarantee that two
separate opens of certificate and key see the same generation. Prefer a single
combined PEM via smtp_tls_chain_files where supported, or a controlled offline
transition. No production configuration is changed by this module.

## Reviewed Windows rotation (experimental)

The SMTP TLS wizard now lists staged generations and reviews certificate/key/chain, the current active generation, main.cf and master.cf SHA-256, terminal journal state, client TLS settings and CA trust. Initial setup remains preview-only; no first-time pointer bootstrap or config write is offered. Rotation requires an existing managed Postfix, a locally valid previous certificate for the same DNS identity, and SELinux disabled or not detected. An explicit confirmation is followed by a fresh SHA review inside the existing deployment lock before the existing durable activation transaction checks and reloads Postfix. Local failure attempts rollback; uncertain outcomes require manual journal review. External editors must be excluded separately. The new GUI does not change main.cf, master.cf, ports, inbound SMTP, routing or Exchange configuration. Enforcing, physical delivery and interrupted-process recovery through this GUI remain unverified. Expired previous material and nonstandard configuration require manual recovery or a separate future deployment workflow.

## Reviewed initial deployment

The reviewed deployment dialog now also permits initial managed TLS setup for Postfix >= 3.4 with no conflicting existing SMTP client certificate settings or unfinished journals, on systems with SELinux disabled/not detected. It previews exact original/candidate main.cf hashes and the unchanged SMTP TLS security level. The existing initial transaction writes its durable backup and prepared journal before switching the generation pointer, then atomically replaces only the smtp_tls_chain_files setting and verifies/reloads Postfix. Rollback restores main.cf and reloads it; the protected generation/pointer can remain staged but unused, and only a recorded same-generation retained pointer is eligible for a reviewed retry. The compatible v1 journal records bootstrap_generation; the updated recovery entry point preserves this field. Old installed recovery helpers may omit it, requiring manual review before retry. Interrupted operations are recoverable from the existing journal, but automatic boot recovery requires a separately installed recovery service. The setting is global for outbound SMTP, not confined to the Microsoft 365 destination. No port, listener, inbound TLS, relayhost, queue or Exchange configuration changes are made. Live delivery remains unverified.

## Reviewed interruption recovery

The deployment dialog can inspect incomplete initial and rotation journals and offer explicit recovery. The review checks the current configuration and active pointer, both journal hashes, private backup contents and metadata, and the original-to-candidate TLS-only change. It refuses overlapping transactions, unexpected configuration changes and unknown journal states. Approval is bound to a SHA-256 plan rechecked under the existing deployment lock; initial recovery uses the existing backup journal, while rotation uses the existing generation recovery. A successful restore checks and reloads the running Postfix service. The previous certificate may be expired; no delivery claim is made. Terminal transactions are not undone by this action. SELinux-active/unknown and stopped Postfix still require manual recovery. No timer, port, connector or queue changes are made. External configuration editors must be excluded separately.

## Reviewed SELinux label repair

The deployment dialog now inspects current and expected SELinux contexts of the selected protected generation, its managed directory, parent and active symlink. Missing/unrecognized context data, pending transaction journals and parent/pointer mismatches prevent automatic repair. Only the managed directory, selected generation directory and its three fixed certificate files may be relabelled. Explicit approval binds the exact path identities, expected/current labels and journal state to a SHA-256 plan rechecked under the deployment lock. restorecon uses no recursive or force flags. The helper rechecks labels, journal hashes, active generation and path identities after applying; partial failure must be re-reviewed. It never changes SELinux mode, policy, booleans, ports or Postfix settings and never reloads Postfix. Context matching alone is not proof of confined Postfix access. Activation, recovery and automatic renewal on Enforcing remain gated pending real VM acceptance.

## Real outbound client TLS acceptance gate (experimental)

The disposable Rocky KVM workflow includes an opt-in client-certificate scenario, enabled automatically for matching changes on the post-RC19 candidate branch. The guest must have a real Enforcing kernel, systemd, expected lab hostname and a root-only current-boot marker. A local synthetic CA signs two client certificates and a server certificate. The actual Postfix smtp process delivers synthetic messages exclusively to a loopback TLS sink that requires client authentication, checks the peer fingerprint and observes the postfix_smtp_t context. The scenario exercises existing product initial-deployment, activation, injected reload failure rollback and interrupted-switch recovery primitives, and restores the guest main.cf baseline. It does not use a cloud tenant or validate the GUI Enforcing apply path. Reboot recovery and actual renewal remain separate acceptance cases. The GUI Enforcing gate remains in force until independently demonstrated.

## Recent AVC diagnostics in GUI

The deployment dialog exposes a read-only recent AVC audit summary, independently of the selected generation. It uses bounded, time-limited ausearch output, checks auditctl status, reports the kernel lost-event counter, deduplicates related audit events and distinguishes enforcing, permissive and unknown denial modes. Unsupported or ambiguous audit formats are counted as unparsed; an absent log result is not a clean verdict. The CLI retains its default today window and offers --recent for the GUI. No raw audit records, key material, policy changes or service operations are exported or performed. Historical hints cannot prove confined process access or authorize Enforcing activation.

## Rocky Enforcing invocation regression

The second real Rocky 9.9 VM run reached certificate staging and failed because the trusted executable adapter resolved /usr/sbin/restorecon to /usr/sbin/setfiles, changing the multi-call binary's invocation mode. SELinux-specific callers now validate the lexical invocation path and resolved executable, while retaining the original tool name. The resolved-path adapter remains unchanged for callers requiring binary identity. The fixture also accepts case-insensitive EHLO and includes bounded synthetic guest failure logs. Three local socket/TLS fixture tests verify the expected certificate, a wrong-but-trusted identity and a missing certificate (the local confined-process check is mocked). This is not proof of actual confined Postfix access; the real VM must pass before any GUI Enforcing gate changes.

## Full candidate context preparation

The third Rocky VM run passed invocation-name handling and reached the exact-context comparison, which failed without recording the differing label fields. Ordinary restorecon normally changes only the type, while the existing verifier requires the whole policy-default label. The candidate preparation helper now reviews all four context fields and file identities before applying nonrecursive restorecon -F only to mismatched files/directories in the selected root-private generation. Symlink, hardlink, insecure mode, or MLS/MCS range changes are refused. The expected policy context, file identity, mode, certificate generation and SELinux mode are rechecked after repair. Existing parent/root labels are not automatically forced by this helper. The disposable VM alone initializes its newly created root with -F and reports expected/current label metadata if preparation fails. The independent GUI reviewed repair still uses ordinary restorecon and may require manual review for a non-type difference. No SELinux policy or production activation gate changes. The specific cause of the third run remains to be confirmed by the next VM result. See restorecon(8): https://man7.org/linux/man-pages/man8/restorecon.8.html .
